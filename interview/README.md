1）问题1：LLMs用的好好的，为什么还需要LangChain？

在大语言模型（LLM）如 ChatGPT、Claude、DeepSeek 等快速发展的今天，开发者不仅希望能“使用”这些模型，还希望能将它们灵活集成到自己的应用中，实现更强大的对话能力、检索增强生成（RAG）、工具调用（Tool Calling）、多轮推理等功能。

1）问题2：我们可以使用GPT 或GLM4 等模型的API进行开发，为何需要LangChain这样的框架？

不使用LangChain，确实可以使用GPT 或GLM4 等模型的API进行开发。

但使用LangChain的好处：

Ø  简化开发难度：更简单、更高效、效果更好。

Ø  开发人员可以更专注于业务逻辑，而无须花费大量时间和精力处理底层技术细节。

Ø  学习成本更低：不同模型的API不同，调用方式也有区别，切换模型时学习成本高。使用LangChain，可以以统一、规范的方式进行调用，有更好的移植性。

Ø  现成的Agent构建方法：LangChain提供了现成的构建Agent的方式。让复杂的逻辑变得结构化、易组合、易扩展。

面：我看你简历上写了做过基于 LangChain 的 RAG 知识库应用。那咱们聊聊数据准备阶段。你平时加载本地文档，比如 Markdown，一般用哪个类？

你：在项目早期，我测试过 UnstructuredMarkdownLoader。这个组件功能很强大，能按照文档的标题层级智能切分。但后来在生产预演时，我发现了一个致命问题：它在特定 Python 版本下会引发“死循环”导致程序完全卡死。 所以后来我根据业务场景，针对性地换成了更轻量级的 TextLoader，或者封装原生的 Python IO 操作。

面：哦？这个卡死的情况很有意思，展开说说。是在什么环境下卡死的？你是怎么定位到原因的？

你：当时的情况是，同一个加载代码，在 Python 3.12 的虚拟环境下运行正常；但我切到了最新的 Python 3.14 环境下，程序一跑到 loader.load() 就无限挂起，终端没有任何报错输出。
我当时排查的逻辑是：

先用断点确认了文件路径没问题，不是找不到文件。

接着我怀疑是网络问题，因为这个库底层依赖了 unstructured 包，而 unstructured 内部为了做智能分词，会调用 NLTK 库。

我查阅了 unstructured 的官方源码和 pyproject.toml 文件，发现它的 requires-python 明确写着 <3.14。这就破案了——底层库并未适配最新版的 Python，导致它在尝试初始化某些 C 扩展或者触发 NLTK 静默下载时，陷入了死锁。

面：不错，排查思路很清晰。那你提到换成了轻量级的方案，具体是怎么做的？两者在底层原理上有什么区别？

你：是的。UnstructuredMarkdownLoader 的底层极其“重”，它为了把文本拆解成 Title、NarrativeText 等元素，引入了大量 NLP（自然语言处理）依赖。
如果只是提取纯文本，我会用 TextLoader。如果对 Markdown 的标题结构有硬性要求，我实际上会推荐使用 LangChain 的 MarkdownHeaderTextSplitter，它完全基于正则表达式，没有 NLTK 的额外依赖，运行速度在毫秒级。这符合我们在工程中“杀鸡焉用牛刀”的原则。

面：如果让你在生产环境彻底规避这种环境兼容问题，你有什么工程上的建议？

你：首先，在版本选择上，AI 领域的环境求稳不求新。截至目前，Python 3.10、3.11 和 3.12 是大模型生态兼容性最好的“黄金版本”，我们团队就应当把生产环境锁死在 3.11 或 3.12，绝不能贸然使用 3.14 这种超前沿版本。
其次，在依赖管理上，我现在全面使用 uv 作为包管理器。我会把项目的依赖固定写在 pyproject.toml 里，锁死具体的依赖版本。在部署时，使用 Docker 将 Python 环境完全隔离，确保本地跑的代码和服务器跑的代码100%一致。

面：很好，懂得用 uv 和 Docker 锁环境，说明你有真实的生产意识。如果有一天，业务确实需要你解析一个极其复杂的带图带表的 PDF，必须用 Unstructured，但在离线内网服务器上，你怎么解决它依赖 NLTK 模型的问题？

你：如果是内网离线环境，绝对不能让程序自动去网上下载 NLTK 数据。
我会提前在有网的环境下，手动下载所需的 punkt、averaged_perceptron_tagger 等数据包，打包进项目的 assets 目录或者基础镜像里，然后通过代码 nltk.data.path.append("本地路径") 强制指定 NLTK 的搜索路径，实现完全离线化加载。
