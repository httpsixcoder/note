# 大模型技术概述与工程实践（2026 工业界版）

> **说明**：本笔记以尚硅谷大模型课程《大模型概述》为基础框架，补充了截至 2026 年 10 月大厂实际落地中的技术选型、架构模式与工程治理经验。基础概念部分保留原文档核心定义，工程实践部分按工业界当前主流做法进行了大幅修订与扩展。


## 第 1 章 大模型基础认知

### 1.1 大模型的定义与度量

大模型通常指参数规模庞大（顶尖模型可达万亿级）、训练数据海量、具备跨任务泛化能力的深度神经网络模型。

**三个核心度量维度**：

| 维度 | 单位 | 含义 | 2026 年典型值 |
|:---|:---|:---|:---|
| 参数规模 | B（Billion） | 模型权重数量 | 开源旗舰 500B–2.8T（总参），激活参数 8B–104B |
| 训练数据规模 | T token（Trillion） | 预训练语料 token 数 | 30T–40T token 级别 |
| 计算规模 | EFLOPs | 训练消耗的总浮点运算量 | 顶尖模型不公开，通常 \(10^{24}\)–\(10^{25}\) FLOPs |

> ⚠️ **易混淆概念**：**计算规模（FLOPs）** 描述“模型理论上做了多少计算”，**算力（FLOPS）** 描述“显卡每秒能算多快”。面试中经常被混淆。

### 1.2 为什么会出现大模型：数据、算力、架构的三重共振

1. **数据范式跃迁**：从人工标注的监督学习转向自监督学习（“预测下一个 token”），可用数据从 \(10^5\)–\(10^9\) token 跃升至 \(10^{12}\)–\(10^{14}\) token。
2. **算力基础设施成熟**：GPU/TPU 算力持续增长，数据并行、张量并行、流水线并行使万卡集群训练成为常态。
3. **Transformer 架构的可扩展性**：在参数、数据、计算量提升时持续获得稳定的性能收益（Scaling Law）。

### 1.3 模型分类（按功能与模态）

**按功能分类**：

| 类型 | 输入 → 输出 | 典型用途 | 2026 代表模型 |
|:---|:---|:---|:---|
| 生成式模型 | 上下文 → token 序列/多模态数据 | 对话、推理、代码生成 | Kimi K3、DeepSeek-V4.1-Flash、Qwen3.8、GLM-5.3、GPT-5 系列 |
| 嵌入模型 | 任意模态 → 固定维度向量 | 语义搜索、RAG 向量检索 | BGE 系列、Qwen3-Embedding |
| 重排序模型 | (query, doc) → 相关性分数 | RAG 精排（Top-N → Top-K） | BGE-Reranker、Qwen3-Reranker |
| 分类/判别模型 | 任意模态 → 标签/概率 | 意图识别、内容审核、路由决策 | 基于 BERT 微调的小模型 |

**按模态分类**（生成模型子类）：
- **语言大模型（LLM）** ：文本 → 文本，如 DeepSeek-V4、Qwen3.8、Kimi K3。
- **多模态理解模型**：文本 + 图像/音频/视频 → 文本，如 Qwen3-VL、GPT-5 视觉模块。
- **多模态生成模型**：文本/图像 → 图像/视频/音频，如 Stable Diffusion、Sora、DALL·E。

### 1.4 AIGC 与 AGI 的边界

- **AIGC**：以生成式模型为核心，在人类提示下自动生成多模态内容，本质是“更聪明的工具”。
- **AGI**：具备跨领域通用认知能力，能自主发现问题并制定解决方案。**截至 2026 年仍未实现**，复杂物理世界交互和随机应变仍是硬瓶颈。

### 1.5 开源的真正含义

大模型由 **模型权重、训练代码、推理代码、训练数据集** 四要素构成。 “开源”通常仅指**开放权重**（可能附带推理代码），训练代码和数据集极少公开。2026 年的许可证格局需要特别留意：

- **MIT / Apache 2.0**：DeepSeek-V4.1-Flash（MIT）、Qwen3.8-27B（Apache-2.0）、GLM-5.3-Flash（MIT）—— 商用最友好。
- **社区/自定义许可**：Kimi K3、部分 Llama 衍生模型—— 需逐条阅读条款。
- **仅权重可用**：多数“开源”模型本质是 open-weight，不是 OSI 定义的开源软件。


## 第 2 章 架构演进与训练范式

### 2.1 从 RNN 到 Transformer：为什么最终是它

Transformer 胜出的三个工程原因：
1. **并行计算**：摒弃 RNN 的时间步串行，整个序列可并行训练。
2. **全局依赖直接建模**：任意两个 token 之间一步注意力计算，无需多步传递。
3. **可扩展性**：参数、数据、计算量增加时，Test Loss 稳定下降。

### 2.2 为什么现代 LLM 是 Decoder-Only

| 架构 | 核心特点 | 为何未成为 LLM 主流 |
|:---|:---|:---|
| Encoder-Only | 输出固定维度向量，擅长表征学习 | 不适合生成任务 |
| Encoder-Decoder | 输入输出严格分离，适合翻译 | 自由对话场景下“输入/输出”切分不自然；参数分散在两个模块，生成效率低 |
| **Decoder-Only** | **自回归生成，参数集中于生成建模** | **普适性最好，参数利用率最高** |

**Decoder-Only 自回归流程**：文本 → 分词（Tokenize）→ Embedding → 自注意力 + 前馈层（重复 N 层）→ 下一个 token 概率分布 → 采样 → 追加到输入 → 循环。

### 2.3 训练范式：预训练 → SFT → RLHF/RLAIF

这是现代 LLM 的标准训练流水线：

1. **预训练（Pre-training）** ：海量语料上“预测下一个 token”，获得基础语言能力。**此时模型会“接话”，但不会“对话”**。
2. **SFT（监督微调）** ：高质量指令-回答对，让模型学会“按指令回答”。**靠模仿数据，对安全边界和答案优劣的把握不稳定**。
3. **RLHF/RLAIF（偏好对齐）** ：引入人类或 AI 的偏好信号（哪个回答更好/更安全），优化模型输出分布。**在多轮诱导和边界保持上显著优于纯 SFT**。

> 🎯 **面试要点**：SFT 解决“会不会答”，RLHF/RLAIF 解决“答得好不好、安不安全”。

### 2.4 算力基础设施的工程现实

- **训练瓶颈顺序**：显存容量 → 多卡通信 → 单卡算力。显存不足时数据卸载到 RAM/硬盘，I/O 成为第一瓶颈。
- **推理瓶颈顺序**：显存容量 → 显存带宽（Decode 阶段逐 token 生成，计算单元大量时间在等数据）→ 多卡通信 → Prefill 阶段算力。
- **CUDA 生态**：NVIDIA 的护城河不在峰值算力，而在 CUDA 把理论性能转化为可用性能的能力。2026 年这一格局仍未根本改变。


## 第 3 章 大模型工程实现（2026 工业界版）

大模型落地的五大模块：**提示词工程、RAG、微调、续训、Agent/Workflow**。工业界的共识是：**按“提示词 → 示例 → RAG → 微调 → 续训 → Agent”的顺序逐级升级**，不要一上来就上最重的方案。

### 3.1 提示词工程：从“技巧”转向“需求表达”

早期（GPT-3 时代）需要复杂的思维链、思维树技巧；**现代模型指令遵循能力大幅提升后，复杂技巧的边际收益显著下降**。工业界现在的重点是**结构化、无歧义地表达需求**。

**提示词五要素（通用框架）** ：

1. **角色/任务**：你是谁、你要做什么。
2. **上下文**：稳定参考资料 + 历史对话摘要（非必须）。
3. **输入数据**：本轮用户输入。
4. **输出要求**：格式（表格/JSON）、字段、语言、风格。
5. **约束**：信息来源限制、禁止行为、不确定性处理规则。

**消息结构设计（System / User / Assistant）** ：
- **System**：角色、任务、稳定上下文、输出要求、约束（不随对话变化）。
- **User**：用户本轮输入 + 动态上下文。
- **Assistant**：模型历史输出，追加到消息列表末尾以维持多轮记忆。

**提示词模板**：把可变部分抽象为占位符（如 `{persona}`、`{task}`、`{input_data}`），由 LangChain 等框架在运行时填充。**五要素是内容清单，模板是结构容器，消息结构是运行时装配方式**。

### 3.2 RAG：2026 年“Naive RAG 已死”，进入 GraphRAG / Agentic RAG 阶段

**Naive RAG 的三大结构性缺陷**（2026 年行业共识）：
1. **碎片化检索丢失全局观**：Top-K 文本块拼接无法回答“总结三年战略演变”类宏观问题。
2. **缺乏多跳推理能力**：A→B→C 的链式关系，单次向量检索无法完成。
3. **没有跨会话长期记忆**：每次会话从零开始，用户偏好和历史全部丢失。

**2026 年主流的 RAG 演进方向**：

| 方案 | 解决什么问题 | 代价 / 适用场景 |
|:---|:---|:---|
| **GraphRAG** | 多跳推理、全局摘要 | 索引成本高；适合知识图谱/实体关系密集场景（微软 GraphRAG 已成 Fortune 500 知识引擎标配） |
| **Agentic RAG** | 自主规划检索：查什么、查几次、如何合并 | 延迟和成本上升；适合复杂对比/多文档推理 |
| **混合检索（Dense + Sparse → RRF → Cross-Encoder 重排）** | 提升召回和排序精度 | **简单事实型问题仍应走轻量链路**，全上 Agentic RAG 是过度工程 |
| **分层记忆系统** | 跨会话长期记忆 | 短期记忆存最近对话，中期记忆走向量库（用户偏好/历史摘要），长期记忆存业务实体（客户/订单/合同） |

> **工业界选型建议**：**默认链路 = 混合检索 + RRF 融合 + 重排序；仅当问题明确涉及多跳、全局摘要或复杂对比时，才升级到 GraphRAG / Agentic RAG。** 不要为了“先进”而牺牲简单问题的延迟和成本。

### 3.3 微调与续训：分清场景，不要混用

| | 微调（SFT / PEFT） | 续训（Continued Pre-training） |
|:---|:---|:---|
| **目的** | 改善指令遵循、风格、格式、话术 | 弥补领域语言/知识的系统性缺失 |
| **数据量** | 通常数万到数十万条高质量样本 | 比微调高一个数量级，大量领域文本 |
| **典型信号** | 提示词反复调效果不好，但模型“读得懂”输入 | 模型对领域专有名词、工艺流程缺乏基本理解，拿到正确资料也推不对 |
| **工业界首选** | **PEFT（LoRA/QLoRA）** ——冻结大部分参数，只训练极少量新增参数 | 成本极高，仅在微调无效且问题确属“领域语言缺失”时考虑 |

### 3.4 Agent 与 Workflow：企业级落地的核心战场

#### 3.4.1 Agent 的四个要素（按实际必要性排序）

| 要素 | 是否必须 | 说明 |
|:---|:---|:---|
| **行动（Action）** | ✅ 必须 | 没有行动只是聊天机器人，不是 Agent |
| **工具（Tool）** | 几乎总是存在 | 与外部系统交互的接口 |
| **规划决策（Planning）** | 有条件存在 | 复杂任务才需要显式 Planner |
| **记忆（Memory）** | 最容易被低估 | 长期记忆是生产级 Agent 的分水岭 |

#### 3.4.2 为什么很多 Agent 项目卡在 PoC：架构与治理，而非模型

2026 年企业实践表明，Agent 从 Demo 到生产的主要障碍**不是模型能力，而是架构设计、工具治理、数据质量和运维体系**。

**企业级典型架构：Planner + 专能 Agent**：

```text
用户请求
    ↓
Planner Agent（任务拆分与路由）
    ↓
┌──────────┬──────────┬──────────┬──────────┐
│ 数据Agent │ 知识库Agent│ 代码Agent │ 流程Agent │
│ SQL/分析  │ RAG/文档  │ 代码/测试 │ 审批/编排 │
└──────────┴──────────┴──────────┴──────────┘
    ↓
结果汇总 → 输出
```

**核心原则**：**让每个 Agent 只做自己擅长的事**。一个 Agent 包揽所有步骤（如采购审批中的查预算、查供应商、查历史、判断规则、生成建议）极易失控。

**工具治理（生产事故的主要来源）** ：
- **版本管理**：每个工具维护 `name + version`，接口升级不能让所有 Agent 同时失效。
- **幂等机制**：避免重复调用造成重复扣款/重复提交。
- **安全分层**：查询类操作与写入类操作严格区分，写入需增加用户确认与审计。

#### 3.4.3 MCP：2026 年 Agent 工具接入的事实标准

**MCP（Model Context Protocol）** 由 Anthropic 于 2024 年 11 月提出，2025 年 12 月捐赠给 Linux Foundation 的 Agentic AI Foundation。截至 2026 年初，**超过 10,000 个活跃 MCP Server 在生产环境运行，月 SDK 下载量达 9700 万次**。

**MCP 解决的核心问题**：Function Calling 时代，每个 AI 应用 × 每个工具都要单独适配（\(n \times m\)）；MCP 把工具提供方标准化为 MCP Server，把调用方标准化为 MCP Client，变成 \(n + m\)。

**2026 年企业级 MCP 落地的三个关键设计模式**：

1. **中心注册表（Central Registry）** ：所有已审批的 MCP Server 及其连接元数据的唯一可信源，客户端调用前先查询注册表完成权限和状态校验。Pinterest 的生产实践证实了这一模式的有效性：月调用 66,000 次，覆盖 844 名活跃用户，每月节省约 7,000 工时。
2. **领域隔离的 MCP Server**：不要做一个“万能单体 MCP Server”。按领域拆分（如 Presto、Spark、Airflow 各一个 Server），**抑制上下文膨胀，支持细粒度访问控制**。
3. **双层授权 + 人工审批**：终端用户 JWT 控制人工访问，服务网格身份控制服务间调用；敏感操作（写操作）必须经过人工审批（elicitation）后再执行。

> ⚠️ **工业界注意**：MCP 标准化了“发现和调用工具”，但**尚未标准化生产规模下的身份传播、工具超时预算和结构化错误语义**。企业落地时需要自行补齐这三层基础设施，否则会在生产环境中遭遇工具调用不可观测、超时失控和错误无法自愈的问题。

#### 3.4.4 Workflow：确定性优先时的正确选择

当任务流程固定、规则明确时，**Workflow 的稳定性和可解释性优于 Agent**。工业界趋势是把 Workflow 作为独立于 Agent 的部署单元，而不是强行塞进 Agent 的规划循环。Dify、Coze 等平台均将 Workflow 作为与 Agent 并列的一等公民。


## 第 4 章 2026 开源模型选型速查（面试与工程参考）

| 模型 | 总参 / 激活 | 许可证 | 突出能力 | 适用场景 |
|:---|:---|:---|:---|:---|
| **Kimi K3** | 2.8T / 104B | 开放权重 | Terminal-Bench 2.1 **88.3**；1M 上下文 | 综合能力最强，长上下文任务 |
| **DeepSeek-V4.1-Flash** | 552B / 8–16B | **MIT** | Terminal-Bench 2.1 **90.6**；1M 上下文；稀疏 MoE 效率极高 | 商用最友好，高吞吐推理 |

1. **许可证先过滤**：商用产品优先 MIT / Apache 2.0。
2. **部署约束定规模**：单卡 24GB → 优先 Dense 27B 级；多卡集群 → 考虑 MoE 旗舰。
3. **任务匹配**：代码/Agent 任务看 Terminal-Bench / SWE-bench；长文档看上下文窗口；多模态看 VL 系列。


## 第 5 章 工业界常见误区与面试要点

### 5.1 六个高频误区

| 误区 | 正确认知 |
|:---|:---|
| “模型越大越好” | 先算清延迟、成本和许可证，**单卡可跑的 Dense 27B 在很多任务上已经够用** |
| “上 Agent 才能叫 AI 应用” | 流程固定、规则明确的场景，**Workflow 的稳定性和可维护性远优于 Agent** |
| “RAG 就是向量检索” | 2026 年的 RAG 是 **混合检索 + 重排 + 按需 Graph/Agentic 升级 + 分层记忆** 的完整链路 |
| “Function Calling 和 MCP 是一回事” | Function Calling 是模型输出调用意图的机制；**MCP 是工具发现、调用和治理的协议层**，解决的是工程标准化问题 |
| “提示词技巧决定效果上限” | 现代模型上，**结构化表达需求 + 合适示例** 的收益远大于复杂技巧；效果瓶颈通常在数据质量和工具治理 |
| “微调可以替代 RAG” | 微调固化的是**行为模式和风格**；知识密集、需要引用来源、频繁更新的场景，**RAG 是更合适的架构** |

### 5.2 面试高频问题

1. **“Decoder-Only 为什么成为主流？”** —— 参数利用率高、自由对话不需要硬切分输入输出、自回归与生成任务天然契合。
2. **“SFT 和 RLHF 的分工是什么？”** —— SFT 学“怎么答”，RLHF/RLAIF 学“答得更好更安全”；安全边界和多轮诱导下 RLHF 显著更稳。
3. **“Naive RAG 的问题是什么？”** —— 碎片化丢失全局观、缺乏多跳推理、无跨会话记忆。对应方案：GraphRAG、Agentic RAG、分层记忆。
4. **“企业级 Agent 为什么需要 Multi-Agent？”** —— 单 Agent 包揽多步骤任务容易失控；Planner + 专能 Agent 提高准确率和可维护性。
5. **“MCP 解决了 Function Calling 的什么问题？”** —— 从 \(n \times m\) 适配降为 \(n + m\)；工具发现、能力协商、标准化调用；但仍需补齐身份传播、超时预算和错误语义等生产级基础设施。
6. **“什么情况下用微调，什么情况下用 RAG？”** —— 行为/风格/格式问题 → 微调（优先 PEFT）；知识缺失/需引用/频繁更新 → RAG；领域语言系统性缺失 → 续训。


> **总结**：2026 年大模型工程的核心竞争力，**不在“会不会调 API”，而在“能不能把不确定的模型能力装进确定的工程系统里”**。模型选型看许可证和部署约束，RAG 按需升级不盲目堆叠，Agent 先解决工具治理和记忆分层，MCP 是工具接入的协议底座但生产级仍需自建治理层。这些才是面试和实际工作中真正区分“会用”和“懂行”的地方。
